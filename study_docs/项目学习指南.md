## 1. 项目总览

### 1.1 这个项目是什么

本项目是一套**腿式机器人（四足 / 双足）运动控制的深度强化学习训练框架**，完整复现了 ETH Zurich 机器人系统实验室（RSL）的论文成果：

> *Learning to Walk in Minutes Using Massively Parallel Deep Reinforcement Learning*（arXiv:2109.11978）

其核心思想是：利用 NVIDIA Isaac Gym 的 **GPU 并行物理仿真**，同时运行数千个机器人仿真环境收集数据，使得原本需要数天的训练**在单张消费级 GPU 上几十分钟内完成**，并且训练出的策略可以直接迁移到真实机器人（Sim-to-Real）。

### 1.2 工作区的三大组成部分

| 目录 | 来源 | 作用 |
|---|---|---|
| `isaacgym/` | NVIDIA Isaac Gym Preview 4 | GPU 物理仿真引擎（已解压，另有压缩包 `IsaacGym_Preview_4_Package.tar.gz`） |
| `legged_gym_study/` | ETH RSL `legged_gym` 仓库（master 分支） | 机器人**环境**定义：观测、动作、奖励、地形、课程 |
| `rsl_rl/` | ETH RSL `rsl_rl` 仓库（v1.0.2 标签） | 强化学习**算法**库：PPO 实现，全 GPU 运行 |

三者关系一句话概括：

```
legged_gym（环境）  --观测/奖励-->  rsl_rl（PPO算法）  --动作-->  legged_gym（环境）
        |                                ^
        +------ isaacgym（物理仿真底座）---+
```

依赖关系：`legged_gym` 依赖 `isaacgym`（仿真）和 `rsl_rl`（算法），`rsl_rl` 只依赖 PyTorch，三者均以 `pip install -e .` 方式安装为可编辑包。

### 1.3 能做什么

项目内置 4 种机器人、5 个注册任务（见 `legged_gym/envs/__init__.py`）：

| 任务名 | 机器人 | 环境类 | 说明 |
|---|---|---|---|
| `anymal_c_flat` | ANYmal C（四足） | `Anymal` | 平地行走，带 SEA 执行器网络 |
| `anymal_c_rough` | ANYmal C（四足） | `Anymal` | 复杂地形（坡/楼梯/障碍）课程学习 |
| `anymal_b` | ANYmal B（四足） | `Anymal` | 复杂地形 |
| `a1` | Unitree A1（四足） | `LeggedRobot` | 复杂地形（最常用入门任务） |
| `cassie` | Cassie（双足） | `Cassie` | 双足行走 |

工作区 `logs/flat_anymal_c/` 中已存在一次训练记录，说明环境已经跑通过。

> ⚠️ 注意：该项目已被官方归档，后续维护转移到 [Isaac Lab](https://github.com/isaac-sim/IsaacLab)。但作为学习 RL + 腿式机器人控制的教材，本代码库结构清晰、规模适中，仍然是最佳入门材料之一。

## 3. 强化学习方法原理（PPO 详解）

本章讲解项目使用的算法——PPO（Proximal Policy Optimization），并将每个数学概念对应到 `rsl_rl` 中的实际代码。

### 3.1 从 MDP 到 Actor-Critic

机器人行走被建模为马尔可夫决策过程（MDP）：每个时刻策略网络观察状态 `s_t`，输出动作 `a_t`，环境返回奖励 `r_t` 和新状态。目标是最大化累计折扣奖励的期望：

```
J(θ) = E[ Σ_t γ^t · r_t ]        γ = 0.99（折扣因子）
```

项目采用 **Actor-Critic** 架构（`rsl_rl/modules/actor_critic.py`）：

- **Actor（策略网络）π_θ**：输入观测，输出动作分布的均值 μ(s)。结构为 MLP `[512, 256, 128]`，激活函数 ELU。
- **Critic（价值网络）V_φ**：输入观测，输出状态价值估计（标量）。同样是 `[512, 256, 128]` MLP。
- **探索噪声**：动作标准差 σ 是一个**与状态无关的可学习参数**（`nn.Parameter`，初始 1.0），动作从正态分布采样：`a ~ N(μ(s), σ²)`。训练时随机采样以探索，部署时直接取均值（`act_inference`）。

```python
# actor_critic.py 核心逻辑
def update_distribution(self, observations):
    mean = self.actor(observations)
    self.distribution = Normal(mean, mean*0. + self.std)   # σ 与状态无关
```

### 3.2 PPO 的截断策略损失

PPO 的核心是限制每次策略更新的幅度，防止"一步走错毁掉策略"。定义新旧策略的概率比：

```
ratio(θ) = π_θ(a|s) / π_θ_old(a|s)
```

损失函数取未截断与截断版本的较大值（最小化时等价于取悲观点）：

```
L = max( -A·ratio,  -A·clip(ratio, 1-ε, 1+ε) )      ε = 0.2（clip_param）
```

对应代码（`ppo.py` 的 `update()`）：

```python
ratio = torch.exp(actions_log_prob_batch - old_actions_log_prob_batch)
surrogate = -advantages_batch * ratio
surrogate_clipped = -advantages_batch * torch.clamp(ratio, 1.0-clip_param, 1.0+clip_param)
surrogate_loss = torch.max(surrogate, surrogate_clipped).mean()
```

**直觉**：当优势 A>0（好动作）时，ratio 最多被鼓励增大到 1.2；A<0（坏动作）时，ratio 最多被压到 0.8。超出范围后梯度为零，更新自然停止。

### 3.3 GAE 优势估计

优势函数 A(s,a) 衡量"某动作比平均水平好多少"。项目使用 **GAE（广义优势估计）**（`rollout_storage.py` 的 `compute_returns`）：

```
δ_t = r_t + γ·V(s_{t+1})·(1-done) - V(s_t)          # TD 残差
A_t = δ_t + γλ·A_{t+1}                               # 反向递推，λ = 0.95
Return_t = A_t + V(s_t)
```

λ 在"偏差-方差"之间权衡：λ=0 退化为单步 TD（偏差大、方差小），λ=1 退化为蒙特卡洛（方差大）。λ=0.95 是经验甜点位。

计算完成后对整个 buffer 的优势做**标准化**（减均值除标准差），这是稳定训练的关键技巧：

```python
self.advantages = (self.advantages - self.advantages.mean()) / (self.advantages.std() + 1e-8)
```

### 3.4 完整损失与训练细节

总损失 = 策略损失 + 价值损失 − 熵奖励：

```python
loss = surrogate_loss + value_loss_coef * value_loss - entropy_coef * entropy.mean()
#      value_loss_coef=1.0, entropy_coef=0.01（鼓励探索，防止过早收敛）
```

价值损失也做了截断（`use_clipped_value_loss=True`），防止价值网络单次更新过猛。

**KL 自适应学习率**（本项目特色，`schedule='adaptive'`）：每次更新前计算新旧策略分布的 KL 散度，动态调节学习率：

```python
if kl_mean > desired_kl * 2.0:    lr /= 1.5   # 步子太大 → 缩小（下限 1e-5）
elif kl_mean < desired_kl / 2.0:  lr *= 1.5   # 步子太小 → 放大（上限 1e-2）
# desired_kl = 0.01
```

这相当于给 PPO 又加了一层"信任域"自动控制，对超参数更鲁棒。

**超时的价值引导（Timeout Bootstrapping）**——一个容易忽略但非常重要的细节（`ppo.py` 的 `process_env_step`）：

```python
if 'time_outs' in infos:
    rewards += gamma * values * time_outs
```

机器人摔倒（终止）时价值归零是合理的，但 episode 因**超时被截断**时，状态其实还有价值。若不补偿，Critic 会错误地把"活满 20 秒的好状态"学成零价值。这行代码把超时状态的引导价值加回奖励，是理论与实践一致性的关键。

### 3.5 On-Policy 训练循环

`OnPolicyRunner.learn()` 的主循环：

```
重复 max_iterations 次：
  1. Rollout：用当前策略在 4096 个并行环境中各走 24 步
     → 收集 4096×24 = 98304 条转移 (s, a, r, done, V, log_prob)
  2. 用最后的 Critic 输出做 GAE，计算 returns 和 advantages
  3. 更新：对数据做 5 个 epoch × 4 个 mini-batch（每批 24576 条）的梯度下降
  4. 记录日志，每 50 次迭代保存模型
```

每次迭代约 10 万条样本，这是"几分钟学会走路"的数据基础。

## 4. 系统架构与训练数据流

### 4.1 整体架构图

```
┌─────────────────────────── 一张 GPU ───────────────────────────┐
│                                                                │
│  train.py                                                      │
│    │  task_registry.make_env() / make_alg_runner()             │
│    ▼                                                           │
│  ┌─────────────────────┐        ┌───────────────────────────┐  │
│  │  legged_gym (环境)   │        │  rsl_rl (算法)             │  │
│  │                     │ obs/r  │                           │  │
│  │  LeggedRobot        │───────▶│  OnPolicyRunner           │  │
│  │  ├─ 4096 个并行环境  │        │    ├─ RolloutStorage      │  │
│  │  ├─ 地形/课程/随机化 │        │    ├─ PPO                 │  │
│  │  ├─ 奖励计算         │◀───────│    └─ ActorCritic (MLP)   │  │
│  │  └─ PD 力矩计算      │  action│                           │  │
│  └────────┬────────────┘        └───────────────────────────┘  │
│           │ 力矩指令                                            │
│           ▼                                                    │
│  ┌─────────────────────┐                                       │
│  │  Isaac Gym (PhysX)   │  物理仿真，全部状态以 GPU 张量存储     │
│  └─────────────────────┘                                       │
└────────────────────────────────────────────────────────────────┘
```

关键点：**物理仿真、观测计算、奖励计算、神经网络前向/反向传播全部在 GPU 上**，中间没有任何 CPU-GPU 数据拷贝（通过 `gymtorch.wrap_tensor` 零拷贝共享物理引擎的张量内存）。这就是大规模并行的性能来源。

### 4.2 时间的三个尺度

| 尺度 | 频率 | 说明 |
|---|---|---|
| 物理仿真步 | 200 Hz（dt = 0.005s） | PhysX 积分步长 |
| 控制/策略步 | 50 Hz（decimation = 4） | 神经网络每 4 个仿真步输出一次动作，期间 PD 控制器持续跟踪目标 |
| 指令重采样 | 0.1 Hz（每 10s） | 随机化目标速度指令 |
| episode 长度 | 20s = 1000 策略步 | 超时即重置 |
| 随机推搡 | 每 15s 一次 | 给基座一个随机水平速度冲击 |

**为什么需要 decimation（控制抽取）？** 神经网络不必在物理级别的高频下决策。50Hz 的策略频率对行走足够，同时让一次策略调用等效于"持续 20ms 的动作"，减少了序列长度和方差，也让 PD 控制器把高频抖动滤掉。

### 4.3 一个 `step()` 内部发生了什么

`legged_robot.py` 的 `step(actions)`：

```python
actions = clip(actions)                        # 1. 裁剪动作
for _ in range(decimation):                    # 2. 重复 4 次：
    torques = PD(actions)                      #    - 由动作算 PD 力矩
    gym.simulate(sim)                          #    - 物理推进一步
    gym.refresh_dof_state_tensor(sim)          #    - 刷新关节状态
post_physics_step():                           # 3. 策略步收尾
    刷新基座状态/速度/投影重力
    到点重采样指令；heading 模式换算；测地形高度；随机推搡
    check_termination()                        #    - 基座触地 or 超时 → reset_buf
    compute_reward()                           #    - 遍历所有奖励函数加权求和
    reset_idx(需要重置的环境)                    #    - 课程升级/降级 + 状态重置
    compute_observations()                     #    - 拼接观测向量 + 加噪
返回 (obs, privileged_obs, reward, done, extras)
```

### 4.4 类继承体系

```
BaseConfig（递归实例化配置基类，utils 之外的基础设施）
    └─ LeggedRobotCfg ──▶ A1RoughCfg / AnymalCRoughCfg ──▶ AnymalCFlatCfg ...
    └─ LeggedRobotCfgPPO ──▶ A1RoughCfgPPO / ...

BaseTask（base_task.py：sim/viewer 创建，渲染循环，buffer 分配）
    └─ LeggedRobot（legged_robot.py：MDP 全部实现 + 17 个奖励函数）
         └─ Anymal（anymal.py：覆盖 _compute_torques，接入执行器网络）
         └─ Cassie（cassie.py：双足定制）
    A1 直接使用 LeggedRobot 类，只是换了配置（a1_config.py）
```

**配置系统的设计很巧妙**（`base_config.py`）：配置写成"类嵌套类"，`BaseConfig.__init__` 递归地把所有成员类实例化，使得 `cfg.rewards.scales.tracking_lin_vel` 这样的点号访问可用，同时支持多继承覆盖——子任务只需覆盖差异项。`class_to_dict()` 再把它转成普通字典传给算法端。

**任务注册**（`task_registry.py`）：环境类、环境配置、训练配置三元组通过 `task_registry.register(name, EnvClass, EnvCfg, TrainCfg)` 注册到全局注册表，命令行 `--task=a1` 即按名字查找。

## 5. MDP 设计详解

强化学习落地的成败，80% 在 MDP 设计。本章逐项拆解观测、动作、奖励的设计及其**背后的动机**。

### 5.1 观测空间（Observation）

以 A1 为例，平地任务 48 维，复杂地形任务 235 维（`compute_observations()`）：

| 观测项 | 维度 | 缩放 | 说明与设计意图 |
|---|---|---|---|
| 基座线速度 | 3 | ×2.0 | **机体坐标系**下（`quat_rotate_inverse`），真实机器人可用状态估计器获得 |
| 基座角速度 | 3 | ×0.25 | 机体系，来自 IMU 陀螺仪 |
| 投影重力 | 3 | — | 重力向量在机体系的分量，等价于 roll/pitch 姿态。**不给绝对朝向 yaw**——因为 yaw 在真实世界不可观且无全局意义（策略应对朝向不变） |
| 速度指令 | 3 | ×缩放 | (vx, vy, wyaw) 目标值，告诉策略"要往哪走" |
| 关节角 − 默认角 | 12 | ×1.0 | 减去默认站姿使数值以 0 为中心，加速学习 |
| 关节速度 | 12 | ×0.05 | 数值较大，缩小保持各维度量纲均衡 |
| 上一步动作 | 12 | — | 让策略感知自己刚下的指令，等效于引入短历史，利于平滑动作 |
| 地形高度 | 187 | ×5.0 | 仅复杂地形：机体周围 17×11 网格点高度（前方 ±0.8m × 侧向 ±0.5m），值= clip(基座高−0.5−地面高, −1, 1)。这是策略的"眼睛" |

要点总结：
- **一切状态量都转到机体坐标系**：策略学到的是"相对于自己"的运动，与全局位置/朝向无关，泛化性更好，也和真实机器人传感器一致。
- **所有量都做了缩放**（`obs_scales`），使各维度数值范围大致在 ±1 量级，对神经网络友好。
- 观测还会**叠加均匀噪声**并裁剪到 ±100（见 6.4 节）。

### 5.2 动作空间与 PD 控制

动作为 12 维向量（每条腿 髋/大腿/小腿 3 个关节），含义是**关节目标位置的偏移量**：

```
目标关节角 q* = action_scale × action + default_joint_angles
              = 0.25 × action + 默认站姿
```

随后由关节级 **PD 控制器**转换为力矩（`_compute_torques`）：

```
τ = kp·(q* − q) − kd·q̇        A1: kp=20, kd=0.5；力矩裁剪到 URDF 限值
```

**为什么不直接输出力矩？** 位置目标 + PD 是学界主流做法，原因：
1. 动作空间有界且平滑，探索更安全（力矩直接控制容易震荡损坏硬件）；
2. PD 提供了"被动柔顺性"，脚落地冲击被吸收，sim-to-real 更鲁棒；
3. 默认站姿作为偏移基准，策略只需学"相对站立姿态的调整"，大幅缩小了搜索空间。

配置也支持速度模式 `'V'` 和纯力矩模式 `'T'`（`cfg.control.control_type`）。

### 5.3 奖励函数（Reward Shaping）

总奖励 = Σ(各奖励项 × 权重 × dt)。`_prepare_reward_function()` 会自动搜集所有**权重非零**的奖励函数（命名为 `_reward_<名称>` 的方法），权重为 0 的项直接被移除。注意：**权重会乘上策略步长 dt=0.02**，把"每秒奖励"转成"每步奖励"。

全部 17 个奖励函数（`legged_robot.py` 815-906 行），按用途分类：

**① 任务目标（正奖励）**

| 奖励 | 默认权重 | 公式 | 意图 |
|---|---|---|---|
| `tracking_lin_vel` | +1.0 | exp(−‖v_xy − cmd_xy‖²/σ) | 跟踪目标线速度，σ=0.25 控制奖惩锐度 |
| `tracking_ang_vel` | +0.5 | exp(−(ω_yaw − cmd)²/σ) | 跟踪目标转向速率 |
| `feet_air_time` | +1.0 | Σ(腾空时间−0.5s)×首次落地 | 鼓励清晰迈步、惩罚拖地走；零速度指令时不给 |

**② 姿态与运动品质（惩罚）**

| 奖励 | 默认权重 | 意图 |
|---|---|---|
| `lin_vel_z` | −2.0 | 惩罚上下颠簸 |
| `ang_vel_xy` | −0.05 | 惩罚俯仰/侧倾角速度 |
| `orientation` | 0（flat 任务 −5） | 惩罚机体倾斜（投影重力 xy 分量） |
| `base_height` | 0 | 惩罚机身高度偏离目标（A1 为 0.25m） |

**③ 能耗与平滑性（惩罚）**

| 奖励 | 默认权重 | 意图 |
|---|---|---|
| `torques` | −1e-5（A1 −2e-4） | 惩罚大力矩 ≈ 节能 |
| `dof_vel` / `dof_acc` | 0 / −2.5e-7 | 惩罚关节速度与加速度，动作更柔顺 |
| `action_rate` | −0.01 | 惩罚相邻步动作突变，防止高频抖动（对实机电机友好） |

**④ 安全约束（惩罚）**

| 奖励 | 默认权重 | 意图 |
|---|---|---|
| `collision` | −1.0 | 大腿/小腿等非足部碰撞 |
| `dof_pos_limits` | 0（A1 −10） | 接近关节角度限位（软限位取 URDF 限位的 90%） |
| `dof_vel_limits` / `torque_limits` | 0 / 0 | 接近速度/力矩限值 |
| `feet_stumble` | 0 | 脚撞竖直面（水平力 > 5×竖直力） |
| `feet_contact_forces` | 0 | 足底冲击力超过 max_contact_force |
| `stand_still` | 0 | 零指令时惩罚关节偏离默认站姿 |
| `termination` | 0 | episode 终止的固定惩罚（在 clip 之后单独加入） |

**两个精妙的设计细节**：

1. `only_positive_rewards=True`：总奖励被裁剪到 ≥0。若允许总奖励为负，"尽快摔倒结束 episode"反而成为局部最优（负奖励累积最少）——机器人会学会"自杀"。裁剪后自杀不再划算。
2. `termination` 奖励在上述裁剪**之后**才加入，保证终止惩罚永远生效，不会被裁掉。

### 5.4 终止条件

```python
reset = (基座等关键部位接触力 > 1N)  or  (episode 超过 20s)
```

- 摔倒（基座触地）→ 终止，无终止奖励时价值归零；
- 超时 → `time_out_buf` 标记，触发 3.4 节的价值引导补偿；
- 重置时：关节角 = 默认站姿 × U(0.5, 1.5)（随机化初始姿态），基座速度 U(−0.5, 0.5)，训练开始时所有环境的 episode 长度还会随机错开（`init_at_random_ep_len`），**避免 4096 个环境同步重置导致的数据分布周期性震荡**。

## 6. 核心训练技术专题

本章讲解项目中最值得学习的五个方法论，它们共同解决了"训得快、训得稳、能上真机"三大问题。

### 6.1 GPU 大规模并行仿真

传统 RL 机器人训练用 MuJoCo 单线程跑几十个环境，而 Isaac Gym 把 PhysX 物理引擎搬到 GPU 上：

- **4096 个环境并行仿真**（`num_envs=4096`），所有状态存为一张大 GPU 张量；
- `gymtorch.wrap_tensor()` 把 PhysX 内部的显存缓冲区直接包装成 PyTorch 张量，**零拷贝**；
- 观测、奖励、PD 力矩计算全部用 PyTorch 向量化完成，天然批处理；
- 结果：单张 RTX 级显卡每秒数万步采样，A1 走平地的策略约 10-20 分钟收敛。

学习要点：这套"环境即张量"的范式（环境不进 Python 循环、不返回 numpy）是 Isaac 系 RL 的根基，写自定义环境时应始终保持全部计算在 torch 张量上完成。

### 6.2 地形与游戏化课程学习（Terrain Curriculum）

复杂地形任务中，地图被组织成 **10 行 × 20 列** 的网格（`terrain.py`）：

- **列 = 地形类型**，按比例分配：平滑坡 10%、粗糙坡 10%、上楼梯 35%、下楼梯 25%、离散障碍 20%；
- **行 = 难度等级**（坡更陡、楼梯更高），共 10 级；
- 每个环境（机器人）被分配到某一个格子，出发点在格子中心。

课程规则（`_update_terrain_curriculum`，机器人 episode 结束重置时执行）：

```
走得足够远（位移 > 地形块长度的一半）    → 升一级（更难）
走得不足指令要求路程的一半            → 降一级（更简单）
通关最高级                            → 随机分配到任意一级复习
```

**思想**：不从头在最难地形上硬训（学不会），也不在固定难度上训（上限低），而是让每个机器人始终在自己的"最近发展区"训练。这与游戏关卡设计同理，故称 game-inspired curriculum。训练日志中的 `terrain_level` 指标反映整体进度。

### 6.3 指令课程（Command Curriculum）

另一路课程作用于速度指令（`update_command_curriculum`）：

```python
# 当跟踪奖励达到最大值的 80% 时，认为当前指令范围已掌握
if mean(episode_sums["tracking_lin_vel"]) > 0.8 * scale * episode_len:
    lin_vel_x 指令范围向正负各扩大 0.5 m/s（上限 max_curriculum=1.0）
```

即"先学慢走，再学快走"。注意评估是按 episode 边界、跨环境聚合的，避免每步都调整造成不稳定。

### 6.4 域随机化与观测噪声（Sim-to-Real 的核心手段）

真实机器人与仿真存在差距（reality gap）：摩擦系数不准、质量分布偏差、传感器噪声、通讯延迟、未建模扰动……对策是**在仿真中主动注入随机性**，让策略对这些变化鲁棒：

| 随机化项 | 配置 | 实现 |
|---|---|---|
| 地面摩擦 | U(0.5, 1.25) | 64 个摩擦"桶"，每个环境随机分配（`_process_rigid_shape_props`）。分桶是为避免 4096 次逐形状赋值的开销 |
| 基座附加质量 | U(−1, +1) kg | 修改刚体属性（`_process_rigid_body_props`），模拟背负载荷/电池误差 |
| 随机推搡 | 每 15s，xy 速度 ±1 m/s | 直接覆写基座速度，模拟被人踢/撞（`_push_robots`） |
| 观测噪声 | 逐项不同强度 | 均匀噪声 U(−1,1)×各维缩放：关节角 0.01、关节速度 1.5、线速度 0.1、角速度 0.2、重力 0.05、高度 0.1（`_get_noise_scale_vec`） |
| 初始状态 | 关节角 ×U(0.5,1.5)，基座速度 ±0.5 | 见 5.4 节 |

`play.py` 验证时会**关闭**噪声、摩擦随机化和推搡，以评估策略在标称条件下的表现。

### 6.5 执行器网络（Actuator Net）—— 建模真实电机

ANYmal 使用 SEA（串联弹性执行器），其实际力矩响应与理想 PD 差距很大（有延迟、饱和、回滞）。项目的解法非常实用（`anymal.py`）：

1. 先在真实执行器上采集数据，训练一个小型 **LSTM 网络**（2 层 × 8 隐藏单元）拟合"目标位置误差 + 当前关节速度 → 实际输出力矩"的映射；
2. 训练时用这个网络（`torch.jit.load` 加载）替代理想 PD 计算力矩：

```python
sea_input = [位置误差, 关节速度]
torques, (hidden, cell) = actuator_network(sea_input, (hidden, cell))
```

这样策略在仿真中学到的就是"如何驱动真实电机"，而非"驱动理想电机"。LSTM 的隐藏状态按环境维度展开（`num_envs×12` 个独立执行器），重置时清零。这是弥合 sim-to-real 执行器差距的经典手法。

### 6.6 补充：非对称 Actor-Critic 接口

框架支持 Critic 看到比 Actor 更多的信息（`num_privileged_obs`，如真实摩擦系数、无噪声状态）——训练时 Critic 评估更准，部署时 Actor 只依赖机载传感器。本项目默认未启用（`num_privileged_obs=None`），但 `OnPolicyRunner` 和 `RolloutStorage` 已完整支持，是进阶研究（如 Teacher-Student 蒸馏）的现成接口。

| `envs/anymal_c/anymal.py` | 执行器网络（6.5 节）：如何重写 `_compute_torques` 接入 LSTM 执行器模型 |

### 8.6 阅读技巧

1. **先列方法清单再细读**：`grep -n "def " <file>` 快速建立文件地图；
2. **双开配置与实现**：读 `legged_robot.py` 时旁边开着 `legged_robot_config.py`，随时查 `self.cfg.xxx` 的实际取值；
3. **随手标注张量形状**：如 `dof_pos: (num_envs, 12)`、`contact_forces: (num_envs, n_bodies, 3)`——Isaac Gym 代码的正确性很大程度靠形状对齐，读懂形状就读懂了一半；
4. **改着读**：加一行 `print`、改一个奖励权重重新训练，比干读印象深十倍；
5. **遇到 Isaac Gym API 查官方文档**：`isaacgym/docs/index.html` 有完整的 `gymapi` / `gymtorch` 参考。

## 9. 实践指南：自定义与扩展

### 8.1 添加一个新机器人（以文档化的 5 步为准）

1. 在 `envs/` 下新建文件夹，写 `my_robot_config.py`，继承 `LeggedRobotCfg` / `LeggedRobotCfgPPO`；
2. 把 URDF 放入 `resources/robots/my_robot/`，在配置中设置：
   - `asset.file`：URDF 路径；`asset.foot_name`：足端刚体名（用于接触检测和腾空奖励）
   - `init_state.default_joint_angles`：默认站姿（每个关节的角度）
   - `control.stiffness/damping`：PD 增益（可用 `{'joint': 20.}` 通配所有关节）
   - `env.num_actions`：关节数；`num_observations` = 48 + 地形高度数（或按自定义修改）
3. 如需定制行为，新建 `my_robot.py` 继承 `LeggedRobot`，重写目标方法；
4. 在 `envs/__init__.py` 注册：`task_registry.register("my_robot", MyRobot, MyCfg(), MyCfgPPO())`；
5. 调参：先关地形（`mesh_type='plane'`、`measure_heights=False`）走通平地，再开课程。

### 8.2 添加自定义奖励

框架的奖励是**自动发现**机制，加奖励只需两步：

```python
# 1. 在你的环境类中定义方法（名字即配置键）
def _reward_keep_heading(self):
    return torch.square(self.heading_error)

# 2. 在配置的 rewards.scales 中设置非零权重
class scales(LeggedRobotCfg.rewards.scales):
    keep_heading = 0.5     # 设 0 即移除该奖励
```

无需注册、无需修改基类。episode 统计和 TensorBoard 日志（`rew_keep_heading`）自动生效。

### 8.3 调试技巧

- **先小规模跑通**：`--num_envs=16` + 不关渲染，肉眼确认机器人姿态、地形、重置正常；
- `env.debug_viz = True` 可绘制高度采样点（黄点），确认"眼睛"看得对；
- 用 `play.py` 逐关节绘图（`logger.plot_states()`）：目标角度 vs 实际角度、指令速度 vs 实际速度，一眼定位是跟踪问题还是规划问题；
- 奖励异常时打印 `env.episode_sums` 各项占比，找出被某个爆炸项淹没的奖励。

### 8.4 策略部署（Sim-to-Real 出口）

`play.py` 默认执行 `export_policy_as_jit()`：

```python
model = copy.deepcopy(actor_critic.actor).to('cpu')
torch.jit.script(model).save('policy_1.pt')
```

导出的 JIT 模型**只含 Actor**（Critic 仅训练用），且不依赖 PyTorch Python 环境，可在 C++（libtorch）中加载，直接部署到机器人机载电脑。LSTM 策略有专门的 `PolicyExporterLSTM`（把隐藏状态注册为 buffer，并附带 `reset_memory()` 接口）。

> 实机部署时记住：以 50Hz 调用策略、PD 增益与仿真一致、观测构造严格复刻 `compute_observations()` 的顺序与缩放——任何一处不一致都会导致策略失效。

## 附：常见坑速查

1. **`libpython3.8m.so.1.0` 找不到** → `sudo apt install libpython3.8` 或配置 `LD_LIBRARY_PATH`；
2. **GPU 上 trimesh 地形的接触力不准** → 已知 PhysX 问题，足底需加力传感器（README 有示例代码）；
3. **训练很慢** → 确认没有开渲染（按 `v` 关闭）、`use_gpu_pipeline=True`；
4. **奖励全 NaN** → 检查 URDF 关节限位/增益是否合理，调小学习率或增大 `damping`；
5. **策略在实机上抖** → 检查观测顺序/缩放是否与训练一致、控制频率是否 50Hz、`action_rate` 惩罚是否足够。
